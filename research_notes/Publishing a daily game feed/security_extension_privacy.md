## 1. Why sites set X-Frame-Options / CSP frame-ancestors, and what users risk when they are removed

### Takeaway
XFO and CSP `frame-ancestors` exist to stop clickjacking (UI redress): a hostile page loads the victim site invisibly or deceptively in a frame and tricks the logged-in user into clicking. Stripping them hands the "who may frame me" decision from the game publisher to whoever controls the extension's allowed origin; stripping the *whole* CSP header additionally disables the game page's XSS/injection defences (script-src, object-src, base-uri, etc.) whenever it is framed by that origin.

### Cited Findings
- OWASP's Clickjacking Defense Cheat Sheet lists as primary defence preventing the browser from loading the page in a frame via the X-Frame-Options header or CSP `frame-ancestors`; XFO is obsoleted in favour of `frame-ancestors` (CSP Level 2); when both are present modern browsers honour `frame-ancestors` — [OWASP Clickjacking Defense Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Clickjacking_Defense_Cheat_Sheet.html) (via search snippet)
- XFO cannot express an allow-list; `ALLOW-FROM` is not supported in any current browser; meta-tag versions of XFO/frame-ancestors do not work (must be HTTP headers) — [OWASP cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Clickjacking_Defense_Cheat_Sheet.html); [MDN Clickjacking glossary](https://developer.mozilla.org/en-US/docs/Glossary/Clickjacking)
- Chrome Lighthouse guidance: setting XFO `DENY`/`SAMEORIGIN` or CSP `frame-ancestors 'self'`/`'none'` mitigates clickjacking — [Chrome Lighthouse: Mitigate clickjacking with XFO or CSP](https://developer.chrome.com/docs/lighthouse/best-practices/clickjacking-mitigation?hl=en)
- OWASP community page describes clickjacking as tricking a user into clicking something different from what they perceive, using transparent/opaque layered frames — [OWASP Clickjacking](https://owasp.org/www-community/attacks/Clickjacking)
- Real-world precedent for CSP removal being treated as an attack primitive: a 2024–25 campaign of 16 malicious Chrome extensions (~3.2 M users) used `declarativeNetRequest.updateDynamicRules` with `modifyHeaders` to blank the `content-security-policy` response header, enabling unauthorised script injection and data exfiltration; GitLab Threat Intelligence reported them and Google removed them (reported as Jan 2025; write-up dated Feb 2025 — timeline slightly inconsistent across sources) — [GitLab Security Tech Note, Feb 2025](https://gitlab-com.gitlab.io/gl-security/security-tech-notes/threat-intelligence-tech-notes/malicious-browser-extensions-feb-2025/); [Techzine](https://www.techzine.eu/news/security/129236/malicious-extensions-in-chrome-web-store-affected-3-2-million-users); [AdGuard blog](https://adguard.com/en/blog/popular-chrome-extensions-including-ad-blockers-hijacked.html)
- The GitLab note characterised an extension degrading CSP protection *without informed user consent* as a clear breach of Chrome Web Store Program Policies (per search summary of the note) — [GitLab Security Tech Note](https://gitlab-com.gitlab.io/gl-security/security-tech-notes/threat-intelligence-tech-notes/malicious-browser-extensions-feb-2025/)
- The best-known store extension doing this, "Ignore X-Frame headers" (v2.0.0, rewritten on MV3/declarativeNetRequest), itself warns it should be used only temporarily and only for development/testing/troubleshooting because it disables important browser security mechanisms — [Chrome Web Store listing](https://chromewebstore.google.com/detail/ignore-x-frame-headers/gleekbfjekiniecknbkamfmkohkpodhe)

### Inferences
- **Trust is transferred to the allowed origin.** With the current rule, only documents on `localhost`/`127.0.0.1` can frame the listed games header-free. In a public version, the allowed origin becomes e.g. `https://dailygamescroll.example`. Anyone who later controls that origin — via XSS on the site, a compromised hosting/CI account or npm dependency, a sale of the domain, or **domain expiry and re-registration** — can frame nytimes.com (incl. any subdomain, since `requestDomains` matches subdomains, e.g. account/login pages) and the other game sites with no frame protection and no CSP, for every user who still has the extension installed. Users will rarely uninstall a "set and forget" helper extension, so this exposure outlives the project.
- **Clickjacking severity depends on cookies.** In Chrome, third-party cookies remain on by default (section 3), so cookies set `SameSite=None` by a game site would be sent into the framed page, letting a hostile allowed origin overlay/clickjack logged-in actions (subscription, account settings, social sharing). Default `SameSite=Lax` cookies are not sent in cross-site iframes, which limits but does not eliminate the risk. This is reasoning from standard cookie semantics, not a sourced test of NYT's cookies.
- **Whole-CSP removal is broader than needed.** Removing `content-security-policy` deletes `script-src`, `connect-src`, `object-src`, `base-uri`, `form-action`, `upgrade-insecure-requests`, Trusted Types, etc. on the framed game document. If any of those games has an injectable XSS bug that CSP currently neutralises, it becomes exploitable inside the feed. A narrower approach (rewriting only `frame-ancestors` with a `set` operation, or appending the feed origin) would cut this; DNR does not support regex-editing a header value, so in practice the choices are remove vs. replace the whole header with a hand-maintained policy (inference; not verified against current DNR docs because developer.chrome.com was unreachable).
- **`localhost` as initiator is not risk-free either.** Any local web server or locally-run malicious page on `localhost` (dev tools, other apps) gets the same privilege.
- **Breakage risk from initiator matching:** if a framed game navigates itself (redirect, login flow), the new sub_frame request's initiator is the game's own origin, not the feed, so headers are not stripped and the frame may go blank — a functional, not security, issue (inference).

### Gaps
- Could not read the full OWASP cheat sheet or current DNR `modifyHeaders` docs (hosts blocked); exact wording and DNR header-operation details (e.g., whether `append` is allowed for CSP) unverified.
- No source found on actual clickjacking exploits targeting the specific game sites.

## 2. Chrome Web Store and Microsoft Edge Add-ons policy

### Takeaway
Neither store explicitly bans header-modifying extensions — several "ignore X-Frame/CSP" extensions are live in the Chrome Web Store — but both have broad "must not compromise user security" rules, least-privilege permission rules and single-purpose/disclosure rules. A publicly listed extension whose purpose is to weaken nytimes.com's and others' security headers so a third-party site can frame them is plausibly approvable only with prominent disclosure and narrow scope, and carries real rejection/takedown risk, plus potential trademark/brand complaints from framed publishers.

### Cited Findings
- **Chrome "Use of Permissions":** "Request access to the narrowest permissions necessary to implement your Product's features or services. If more than one permission could be used to implement a feature, you must request those with the least access to data or functionality." — [Chrome Web Store Program Policies](https://developer.chrome.com/docs/webstore/program-policies/policies?hl=en) (via search snippet)
- **Chrome single purpose / limited use:** developers must describe the extension's primary functionality in the single-purpose field; extensions may only collect/use/transmit user data necessary for their disclosed single purpose — [Program Policies](https://developer.chrome.com/docs/webstore/program-policies/policies?hl=en); [User Data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq)
- **Chrome deceptive/unexpected behaviour:** policy states changes to device settings must be made with the user's knowledge and consent and be easily reversible; it has sections on "Deceptive Installation Tactics" and "Misleading or Unexpected Behavior"; spyware, malicious scripts and phishing are prohibited — [Program Policies](https://developer.chrome.com/docs/webstore/program-policies/policies); Chrome blog says Google removes extensions that deceive/mislead users or enable dishonest behaviour — [Chrome Web Store Policy Updates blog](https://developer.chrome.com/blog/cws-policy-revamp)
- **2026 Chrome policy changes:** update published 1 Jul 2026, enforced from 1 Aug 2026: stricter data-minimisation to the disclosed single purpose, prominent disclosure of data collection and of later changes, new bans on real-money prediction-market extensions and on extensions built to bypass AI-service safety guardrails/usage limits; all listings re-reviewed against new wording — [CyberInsider](https://cyberinsider.com/google-chrome-extensions-must-meet-new-privacy-standards-by-august-1/); [Todd Schiller, 17 Jul 2026](https://toddschiller.com/blog/extensibility-radar-2026-07-17.html). One blog lists further Oct/Dec 2026 requirements (AI disclosure, third-party audits) that I could not corroborate — [CWS Kit blog](https://cwskit.khanakia.com/blog/chrome-web-store-policy-changes-2026) (unverified). None of the 2026 changes found target header modification specifically.
- 2025: stricter affiliate-ad rules (announced Mar 2025, enforced 10 Jun 2025) per a secondary source — [DeepStrike](https://deepstrike.io/blog/chrome-extensions-security-threats-risk-analysis) (not verified against Google).
- **Edge Add-ons developer policy §1.2 (Security):** "your extension must not jeopardize or compromise user security, or the security or functionality of the device, system, or related systems"; must not exploit vulnerabilities of other extensions/apps; spyware, malicious scripts and phishing prohibited — [Microsoft Edge Add-ons developer policies](https://learn.microsoft.com/legal/microsoft-edge/extensions/developer-policies). Best practice: "Request only the permissions that are necessary for core functionality" — [Edge extension best practices](https://learn.microsoft.com/microsoft-edge/extensions-chromium/developer-guide/best-practices). Every new submission and version undergoes security review; violating items are not allowed — [Edge Add-ons curation and review](https://learn.microsoft.com/en-us/microsoft-edge/extensions-chromium/publish/add-ons-store-curation)
- **Existing extensions of this kind (all live in CWS per search results, Nov 2026):** "Ignore X-Frame headers" (gleekbfjekiniecknbkamfmkohkpodhe, by Guillaume Ryder, v2.0.0 on MV3/DNR, ~4.4★, ~160 ratings on one listing, open source, self-labelled dev/testing only); "ignore-x-frame-options" (ammjifkhlacaphegobaekhnapdjmeclo); "Allow X-Frame-Options" (jfjdfokifdlmbkbncmcfbcobggohdnif); "Awesome XFrame For Site" (jdimfndpfamcnhdhiblhnicoadldlccg, can be limited to one host); Firefox "Ignore X-Frame-Options Header" by ThomazPom — [Ignore X-Frame headers](https://chromewebstore.google.com/detail/ignore-x-frame-headers/gleekbfjekiniecknbkamfmkohkpodhe); [ignore-x-frame-options](https://chromewebstore.google.com/detail/ignore-x-frame-options/ammjifkhlacaphegobaekhnapdjmeclo); [Allow X-Frame-Options](https://chromewebstore.google.com/detail/allow-x-frame-options/jfjdfokifdlmbkbncmcfbcobggohdnif); [Awesome XFrame reviews](https://chrome.google.com/webstore/detail/awesome-xframe-for-site-e/jdimfndpfamcnhdhiblhnicoadldlccg/reviews); [AMO](https://addons.mozilla.org/addon/ignore-x-frame-options-header/)
- Commentators argue CWS enforcement is inconsistent/lax — [palant.info, 13 Jan 2025](https://palant.info/2025/01/13/chrome-web-store-is-a-mess/) (opinion)

### Inferences
- The existence of general-purpose "ignore X-Frame" tools shows the category is tolerated **as user-controlled developer tools with explicit warnings**. A consumer extension tied to one commercial site, stripping protections on third-party brands (NYT etc.) for that site's benefit, looks different to a reviewer: the beneficiary is the publisher, not the user, and the GitLab precedent shows DNR CSP-stripping is a known malware pattern that automated review may flag.
- Compliance levers if publishing anyway: narrowest scope (exact hosts, not `*.nytimes.com`; only `sub_frame`; only the public origin), replace rather than remove CSP, a clear single-purpose description and listing text stating which protections are disabled and for which sites, an off switch, and an open-source repo. Also note `host_permissions` on nytimes.com etc. will produce install-time permission warnings users see (inference; warning wording unverified).
- **Extension-ownership risk:** popular extensions are frequently bought or hijacked and pushed malicious updates (the 16-extension campaign involved compromised developer accounts) — the publisher's developer account itself becomes a high-value target because the extension already holds header-modification power on news/game domains.
- Framed brands (NYT in particular) could file trademark/IP complaints with the stores; Chrome policies also cover impersonation/IP (general knowledge; specific clause not retrieved).

### Gaps
- Could not retrieve the full current text of CWS "Minimum Functionality" and any explicit "security vulnerabilities" clause; no documented case found of an X-Frame-stripping extension being removed or rejected specifically for that behaviour.
- No Edge-specific 2025–2026 policy changes found.

## 3. Browser behaviour that breaks embedded games anyway (cookies, partitioning, Privacy Sandbox)

### Takeaway
Chrome did **not** deprecate third-party cookies (decision July 2024, confirmed April 2025) and retired most Privacy Sandbox APIs in Oct 2025 — but Chrome *has* partitioned third-party storage (localStorage, IndexedDB, service workers etc.) since Chrome 115 (2023), while Safari blocks and Firefox partitions third-party cookies by default. Net effect: a game's saved streaks/stats kept in localStorage will exist separately inside the feed vs. on the game's own site, and logins (especially paid NYT Games) will often not carry over into the iframe outside Chrome-with-default-settings.

### Cited Findings
- Google reversed its third-party-cookie deprecation plan in July 2024; in April 2025 confirmed it would keep its current approach to third-party cookie choice and not roll out a standalone prompt; Chrome keeps 3P cookies on by default with a user setting to block — [usercentrics](https://usercentrics.com/knowledge-hub/what-is-google-privacy-sandbox/); [secureprivacy.ai](https://secureprivacy.ai/blog/google-killed-privacy-sandbox-what-changes-for-cookie-consent-in-2026); [funwithtext.com](https://funwithtext.com/blog/chrome-third-party-cookies-2026.html) (secondary sources; primary Google status page not reachable)
- On 17 Oct 2025 Google retired ten Privacy Sandbox technologies (Topics, Protected Audience, Attribution Reporting, etc.) citing low adoption; CHIPS, FedCM and Private State Tokens reportedly retained; deprecation from Chrome 144 (Jan 2026) with removal targeted at Chrome 150 (~Jul 2026) — [segwise.ai](https://segwise.ai/blog/google-privacy-sandbox-shutdown-reason); [usercentrics](https://usercentrics.com/knowledge-hub/what-is-google-privacy-sandbox/); [ppcrebels](https://ppcrebels.com/en/third-party-cookies-privacy-sandbox-2026/) (secondary; exact removal completion unverified)
- Chrome storage partitioning: "as of Chrome 115, storage, service workers, and communication APIs are partitioned in third-party contexts"; partitioned data "is only available to contexts with the same origin and same top-level site"; an "ancestor bit" partitions when any frame in the chain is cross-site — [Chrome: Storage Partitioning](https://privacysandbox.google.com/cookies/storage-partitioning); [Deprecation trial post](https://developer.chrome.com/blog/storage-partitioning-deprecation-trial)
- Example: an iframe of c.com under a.com, under b.com, and c.com top-level each get separate localStorage — [Chromium extensions forum thread](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/e_3r4XTbzdY) (community post, 2023)
- Storage Access API lets an iframe regain unpartitioned cookies/storage only after calling `document.requestStorageAccess()` (user gesture/permission) — [MDN Storage Access API](https://developer.mozilla.org/docs/Web/API/Storage_Access_API); [Chrome SAA](https://privacysandbox.google.com/3pcd/storage-access-api)
- Firefox: Total Cookie Protection (per-site cookie jars) default in Standard ETP since Firefox 102 — [MDN State Partitioning](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/State_partitioning); [Mozilla Hacks](https://hacks.mozilla.org/2021/02/introducing-state-partitioning/)
- Safari: since 13.1 blocks all third-party cookies by default under ITP; per-frame exceptions only via Storage Access API — [MDN Third-party cookies](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/third-party_cookies); [WebKit blog](https://www.webkit.org/blog/8124/introducing-storage-access-api)

### Inferences
- Since most daily-word/geo games store streaks in localStorage, users will see a **separate, fresh streak inside the feed** on Chrome/Edge (partitioned under the feed's top-level site), and lose it if the feed's domain changes. This is independent of the extension.
- NYT Games subscriber login inside the iframe: may work in default Chrome (3P cookies allowed, if NYT's auth cookies are `SameSite=None`), fail in Safari, Firefox, Brave, Chrome Incognito and for users who block 3P cookies. Unverified for NYT specifically.
- The extension is Chromium-only; Safari/Firefox users of the public site would see blank frames for any game sending XFO/frame-ancestors, so a public site must gracefully degrade (open-in-new-tab link).
- "Privacy Sandbox retirement" does not change partitioning: storage partitioning and CHIPS are separate, still-shipping mechanisms (inference from sources above).

### Gaps
- Chrome Privacy Sandbox status page and current Chrome release notes were not reachable; exact Chrome 150 removal state and any 2026 changes to partitioning unverified.
- Did not test which of the listed games store state in cookies vs. localStorage.

## 4. Privacy/compliance for a public site in Norway/EEA

### Takeaway
From 1 Jan 2025 the new Norwegian ekomloven § 3-15 requires GDPR-standard consent (freely given, specific, informed, unambiguous) for storing/reading non-essential cookies and similar tech; browser default settings no longer count. Under CJEU *Fashion ID* (C-40/17), a site that embeds third-party content which causes visitors' data to be sent to the third party on page load is a joint controller for that collection/transmission — so a feed that auto-loads 10+ third-party game sites (with their analytics/ad trackers) in iframes likely needs prior consent before loading them, a privacy policy, and a record of who receives data.

### Cited Findings
- Ekomloven (lov 13. desember 2024 nr. 76) § 3-15 in force 1 Jan 2025: consent to cookies must meet GDPR consent requirements; previously browser settings permitting cookies sufficed — [Regjeringen: Endringer fra 1. januar 2025](https://www.regjeringen.no/no/aktuelt/endringer-i-lover-og-forskrifter-fra-1.-januar-2025-fra-digitaliserings-og-forvaltningsdepartementet/id3079637/); [CMS Norway](https://cms.law/en/nor/publication/ny-ekomlovgivning); [Usercentrics](https://usercentrics.com/us/knowledge-hub/e-com-act-regulatory-updates-for-cookie-use-in-norway/)
- Delegation regulation: Datatilsynet supervises whether the consent requirement in § 3-15 first paragraph is met (Nkom retains the rest of § 3-15) — [Delegeringsforskrift (regjeringen.no PDF)](https://regjeringen.no/contentassets/0111de0d5d524296aae662e35869f898/forskrift-om-delegering-av-myndighet-etter-lov-13.-desember-2024-nr.-76-om-elektronisk-kommunikasjon-ekomloven-.pdf)
- Datatilsynet reportedly issued detailed cookie-consent guidance on 3 Apr 2025; refusing must not require more clicks/effort than accepting; ekomloven consent does not by itself settle lawfulness of further processing under GDPR; for embedded third-party content (e.g. video) operators should check what data is sent at page load vs. on play and offer alternatives — [Cookie Information blog](https://cookieinformation.com/blog/norwegian-cookie-guidelines-explained/); [Legiscope](https://www.legiscope.com/blog/cookies-norge-ekomloven-kontroll.html) (secondary; Datatilsynet page itself not retrieved)
- Enforcement example: Norwegian SA issued one administrative fine and five reprimands for unlawful sharing of personal data via tracking pixels (final decision 10 Jun 2025) — [EDPB news](https://www.edpb.europa.eu/news/the-norwegian-sa-issues-one-administrative-fine-and-five-reprimands-for-unlawful-sharing-of_fi)
- *Fashion ID* (CJEU C-40/17, 29 Jul 2019): website embedding Facebook's Like button is joint controller with Facebook for **collection and transmission** of visitor data, which happens automatically on page load regardless of clicks/accounts; lack of access to the data is irrelevant; not a controller for Facebook's subsequent processing; operator must obtain prior consent (where consent is the basis) and inform visitors for the operations it co-controls — [CJEU press release](https://curia.europa.eu/jcms/jcms/p1_2278332/ro/); [Hunton](https://www.hunton.com/privacy-and-cybersecurity-law-blog/cjeu-ruling-on-websites-using-facebook-like-buttons); [Bird & Bird](https://www.twobirds.com/en/insights/2019/global/cjeu-fashion-id-case-thumbs-down-to-facebooks-like-feature); [IAPP](https://iapp.org/news/a/how-cjeus-fashion-id-ruling-stripped-sites-of-the-like-button-and-the-cookie-surprise). Decided under Directive 95/46 but applied to GDPR joint-controller analysis — [Thomas Helbing summary](https://www.thomashelbing.com/en/wissen/dsgvo-hub/rechtsprechung/1.4.13-eugh-fashion-id)
- Danish joint guidance (May 2025) explicitly flags embedded third-party plug-ins (e.g. video players) as within cookie rules — [Digst/Datatilsynet DK](https://digst.dk/media/oy1btb02/faellesvejledning-med-datatilsynet.pdf) (Danish, indicative for EEA practice only)
- Privacy Sandbox retirement does not change consent obligations — [secureprivacy.ai](https://secureprivacy.ai/blog/google-killed-privacy-sandbox-what-changes-for-cookie-consent-in-2026)

### Inferences
- An iframe that loads nytimes.com et al. immediately on scroll causes the visitor's browser to set/read those sites' cookies and fire their analytics/ad tags. By analogy to *Fashion ID*, the feed operator "determines the means" of that transmission (choosing to embed and auto-load) and would be a joint controller for it, so: (a) click-to-load placeholders or a consent gate before loading each third-party frame, (b) a privacy policy naming each embedded provider and linking their policies, (c) a consent-management tool if the site itself adds analytics/ads. A purely personal localhost tool falls under the GDPR household exemption; a public site does not.
- A site with only strictly necessary first-party storage and click-to-play frames could avoid a cookie banner for itself, but still needs a privacy notice (GDPR Arts. 13/14).
- Removing third-party CSP may also undercut the games' own data-protection controls (e.g. `connect-src` limiting where data is sent) — a security-of-processing (Art. 32) angle, inference only.

### Gaps
- Lovdata text of § 3-15 and Datatilsynet's own cookie guidance not retrieved directly; Nkom/Datatilsynet role split described inconsistently by secondary sources.
- No Norwegian decision found specifically on iframe-embedded third-party sites.

## 5. Ad networks: AdSense / Google Publisher Policies on framed third-party content

### Takeaway
Yes — Google's publisher policies disallow Google-served ads on screens without publisher content or whose content is mirrored, **framed**, scraped or embedded from others without added value. A feed whose primary content is other publishers' games in iframes is a textbook "Valuable inventory: no content / replicated content" risk unless substantial original content and curation surround it.

### Cited Findings
- Google does not allow ads on screens without publisher content or with low-value content; "Publisher-content includes images, videos, games, article text and user-generated content created or managed by the publisher" — [Google-served ads on screens without publisher-content](https://support.google.com/publisherpolicies/answer/11112688)
- Policy covers "Mirroring, framing, scraping or rewriting of content from other sources without adding value"; "Framing content is when a site or app displays someone else's site within a frame or window without permission from the owners of that content" — [Google-served ads on screens with replicated content](https://support.google.com/publisherpolicies/answer/11190248?hl=en); [AdSense Program policies](https://support.google.com/publisherpolicies/answer/48182)
- Replicated-content policy bars ads on screens "with embedded or copied content from others without additional commentary, curation, or otherwise adding value" — [Replicated content policy](https://support.google.com/publisherpolicies/answer/11190248)
- Enforcement labels publishers see: "Valuable inventory: Templated page" / "Valuable inventory: no content"; third-party advice of ~80/20 original vs. sourced content is not a Google rule — [MonetizeMore](https://www.monetizemore.com/blog/how-deal-with-valuable-inventory-templated-page-violation-adsense)
- Google is consolidating policies into a new Publisher Policies Help Center — [AdSense policies page](https://support.google.com/publisherpolicies/answer/48182)

### Inferences
- The games here are "created or managed" by NYT etc., not the feed publisher, so they likely don't count as publisher content. Additionally, framing sites that explicitly forbid framing (they send XFO/frame-ancestors) is strong evidence of framing "without permission", aggravated if users must install an extension to defeat that refusal.
- Ads next to framed NYT content also raise copyright/trademark and terms-of-service exposure (NYT and others typically prohibit framing in ToS — not verified in this research).

### Gaps
- Full policy pages not fetched (support.google.com blocked); no 2025–2026 changes to these specific policies found.

## 6. Other abuse vectors: phishing/impersonation and Safe Browsing

### Takeaway
Framing famous brands (NYT) inside another domain resembles the techniques Safe Browsing classifies as social engineering; Google's docs warn that a third party operating content on behalf of/appearing as another brand without making the relationship clear "might be flagged". A Safe Browsing "Deceptive site ahead" flag would block the whole public site in Chrome/Firefox/Safari.

### Cited Findings
- Google: deceptive content may enter via embedded resources (images, third-party components, ads); "If you (third party) operate a site on behalf of another (first) party without making the relationship clear, that might be flagged as social engineering"; fix by clearly showing the operating brand; review via Search Console Security Issues report — [Google Search Central: Social engineering](https://developers.google.com/search/docs/advanced/security/social-engineering)
- Safe Browsing's expanded social-engineering coverage targets content imitating a site's look and feel to pose as a legitimate entity — [Trend Micro](https://www.trendmicro.com/vinfo/fi/security/news/cybercrime-and-digital-threats/google-now-warns-against-social-engineering-content)
- Anecdotal: legitimate sites with login-like pages flagged as "Deceptive pages" without obvious cause — [InfinityFree forum](https://forum.infinityfree.com/t/google-safe-browsing-warning-social-engineering-detection/121924.md) (anecdotal)

### Inferences
- Risk factors: NYT login/subscription screens rendering inside a non-NYT domain (a user entering NYT credentials into a framed form on a third-party origin is exactly the pattern phishing training warns against); a compromised feed could overlay fake login prompts atop real-looking framed NYT UI. Mitigations: clear own branding, never frame login/account pages (exclude account subdomains from rules), open sign-in in a new top-level tab, label each card with source + "open on original site".
- Publisher-side complaints (DMCA/trademark) to the host or registrar are another takedown vector.

### Gaps
- No documented case found of a game-aggregator being Safe-Browsing-flagged for framing.
